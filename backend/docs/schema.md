# Database schema (milestones 2–6A)

`users`: application-generated UUID primary key and non-null `created_at`
(`timestamptz`, database `now()` default). There are no identity or auth fields.

`projects`: application-generated UUID primary key, indexed non-null `owner_id`,
non-null `name` (`varchar(100)`), and non-null `created_at` / `updated_at`
(`timestamptz`). `created_at` has a database `now()` default.

`fk_projects_owner_id_users` requires an existing owner and uses `ON DELETE
RESTRICT`. Deleting an owner with projects fails; no ORM cascade or database
cascade is configured. Duplicate names are allowed, including for the same owner.
`ck_projects_name_nonblank` requires a character outside PostgreSQL's POSIX
whitespace class, rejecting empty strings, spaces, tabs, and newlines.
Primary keys use `pk_<table>` and the owner index is `ix_projects_owner_id`.

UUIDs are generated by SQLAlchemy's `uuid4` insert default, not by PostgreSQL.
The supported timestamp write path is SQLAlchemy ORM inserts/updates or SQLAlchemy
Core statements built from the mapped table. `updated_at` uses an aware UTC Python
callable for insert and `onupdate`; it changes when an UPDATE is emitted and no
explicit updated_at value is supplied. A no-op ORM commit leaves it unchanged.
Explicit values override the default. Raw SQL and external writers must supply
and maintain updated_at themselves; no database trigger is installed.
PostgreSQL stores timestamptz instants in UTC. Use UTC database sessions for reads
and aware UTC application values; migration/test sessions explicitly select UTC.

Migrations are explicit. Neither API startup nor health endpoints create tables
or run migrations. The initial migration creates users, projects, and the owner
index; its downgrade removes those application tables. Downgrade is destructive
and is exercised only in a new disposable test database.

## API tokens (milestone 3)

`api_tokens`: application-generated UUID `id`, non-null indexed UUID `user_id`,
non-null `digest` (`varchar(64)`), non-null timezone-aware `created_at` with database
`now()` default, and nullable timezone-aware `revoked_at`. There is no raw-token
column. `uq_api_tokens_digest` creates a unique PostgreSQL index on the SHA-256
hex digest. `fk_api_tokens_user_id_users` uses `ON DELETE RESTRICT`, including
for revoked tokens. UUID and timestamp conventions match the existing models.

Management issuance generates 32 random bytes using Python secrets, encodes them
as URL-safe text with an `lv_` prefix, and hashes the **full token**. It prints raw
token material only after commit. Authentication compares the digest via the
unique index and requires revoked_at IS NULL. Token IDs are management identifiers,
not credentials. Revocation sets revoked_at using the database UTC instant and
preserves the first revocation time on repeated calls. Tokens do not expire in
this initial policy. No default accounts/tokens, identity fields, or cascades exist.

Revision `0002_api_tokens` adds only api_tokens and its indexes. Its downgrade
removes only that table, preserving users/projects, and is tested only in the
fixture-created disposable databases. `0001_users_projects` is unchanged.

## Private artifacts (milestone 5)

`artifacts`: UUID id; non-null indexed UUID project_id referencing projects with
ON DELETE RESTRICT; unique private storage_key (varchar(64)); nonnegative bigint
size_bytes, file_count, declared_uncompressed_bytes; SHA-256 hex sha256
(varchar(64)); and timezone-aware created_at with database now() default.
Constraint names follow the existing pk/fk/uq/ix/ck convention. There are no file
cascades: projects with artifacts cannot be deleted, and metadata deletion is not
exposed. Storage keys are server-generated UUID filenames, never API fields.
Revision 0003_artifacts follows unchanged 0002_api_tokens. Downgrades are tested
only in disposable databases and do not delete files. No existing migration changed.

## Queued execution requests (milestone 6A)

`runs`: application-generated UUID id; non-null indexed project_id FK directly
to projects.id; non-null artifact_id; status varchar(16), default queued and
constrained to queued; runtime_template varchar(32), constrained to
python-fastapi-v1 with no implicit template default; created_at timestamptz with
database now() default. There is no user_id: ownership is derived through projects.

`fk_runs_artifact_project` maps (artifact_id, project_id) to
artifacts.(id, project_id), enforcing consistency even for direct database writes.
The new `uq_artifacts_id_project_id` is logically redundant with the global
artifact PK, but PostgreSQL requires an explicit matching unique target for that
composite FK. It is added only in new revision 0004_runs after 0003_artifacts.
Both the direct project FK and composite artifact FK use ON DELETE RESTRICT.
No metadata/files are cascade-deleted. The downgrade removes runs and the new
pair constraint, preserving artifacts/projects; only disposable tests run it.

Milestone 6A kept all records queued; milestone 6C extends this below. The template is
an explicit client selection, not source-compatibility validation. Milestone 6B
adds idempotency below; different keys produce independent records. No quotas
are implemented.
Future milestones must explicitly migrate the status constraint/schema before
adding lifecycle transitions; no speculative lifecycle columns are present here.


## Milestone 6B: run_idempotency

`0005_run_idempotency` adds a durable retry table without changing existing runs.
Its composite primary key `pk_run_idempotency_scope` is `(user_id, operation, key)`;
key is VARCHAR(128) with PostgreSQL C collation for case-sensitive equality.
User and run foreign keys use RESTRICT; run_id is unique. Fingerprint is the
SHA-256 of deterministic compact, sorted-key JSON containing version=1,
canonical project/artifact UUID strings and runtime_template. Operation is
`run.create`. No key backfill, expiration, or automatic deletion occurs.

The run and key record are inserted in one transaction. PostgreSQL ON CONFLICT
explicitly targeting the scope primary key triggers rollback-and-read of a
concurrent winner; unrelated constraints and database
errors are not suppressed and remain sanitized service failures. Expected
conflicts do not emit database errors containing raw key values. Authorization
is checked before lookup and again after a uniqueness rollback. Local lock_timeout
is 1500ms; existing statement_timeout is 2000ms. Sessions close on every path and
synchronous database calls remain on FastAPI's worker threads.

No raw key is exposed by API responses or logs. Existing runs without retry
records remain accessible. Milestone 6C below now persists the original queued
response for stable 201 replays, while GET shows mutable current state. A new key
intentionally creates a separate run.

## Milestone 6C: lifecycle, jobs, events, immutable creation replay

Revision `0006_simulated_lifecycle` follows unchanged 0005_run_idempotency.
It first asserts every existing run is queued, adds JSONB creation_response to
run_idempotency, and backfills the original six response fields with canonical
UTC timestamp encoding. The column is then non-null. Fingerprint v1 and key
scope are unchanged. No jobs are backfilled and old runs remain unscheduled.

Run status now permits queued, preparing, starting, running, completed, failed.
The shared transition path permits each consecutive success state, or failed
from any nonterminal state. Terminal runs cannot be revived. New updated_at is
non-null timestamptz with now() default; old values are initialized to created_at.
Worker transitions maintain updated_at with database UTC time. Nullable error_code
stores only controlled codes, not exceptions. GET reads mutable status (milestone
7A adds its nullable cancellation timestamp); POST/replay renders stored creation_response,
not the mutable row. Original Location is derived from unchanged project/run IDs.

`execution_jobs` has an application UUID PK, unique restrictive run FK, pending /
leased / completed / failed state, available_at, attempts, max_attempts (default 3),
monotonic fence, nullable lease_owner UUID and lease_until timestamptz, and a
sanitized last_error_code. The availability index supports polling; claim uses
FOR UPDATE SKIP LOCKED. Checks constrain states/attempt bounds and require lease
owner/deadline exactly when leased. Terminal job state records the run result.

Scenario, bounded startup_seconds/duration_seconds, and accepted_at are internal
simulator recovery metadata. Scenario/timing are frozen at first claim from local
configuration; accepted_at anchors the same logical start operation across worker
attempts. No source inspection, local path, executable command, or runner URL is
stored. The stable operation identity is derived from run ID and contract version.

`run_events` has an application UUID PK, restrictive run FK, positive sequence,
status, optional controlled error_code, and database-default UTC created_at. The
unique (run_id, sequence) constraint provides ordering and an index for per-run
reads. Job-then-run locks serialize transition checks and sequence allocation;
state, event, and terminal/retry bookkeeping commit together. Retries do not append
another event for an already persisted state. Events are internal, not a log API.

Creation commits run, job, key, and creation snapshot together. Intended key
conflicts roll back the losing run and job before reading the winning snapshot.
No job is added by replay. Explicit enqueue-run validates queued state and inserts
one job under its unique run FK; repeated queued invocations return the same ID.

Every worker mutation requires its current lease owner/fence and live database
clock deadline after row locking. Renewal also checks expiry in the UPDATE itself.
Expired leases can be reclaimed with a higher fence; attempts count claimed work,
including crashes. Infrastructure failures schedule bounded retries; application
startup failure is immediately terminal; exhausted attempts transition to failed
with retries_exhausted. All SQL waits are bounded and runner operations occur
outside transactions. No deletion cascades or key/job expiry exist.

Downgrade is tested only on disposable databases. It refuses nonqueued runs rather
than rewrite completed/failed history into queued. Development migrations are
upgrade-only: never reset, downgrade, stamp, or delete development volumes.


## Milestone 7A: durable cancellation

0007_run_cancellation adds nullable timestamptz cancellation_requested_at to runs
and extends the run/job state constraints with terminal stopped. Existing statuses,
creation snapshots, request fingerprints, artifacts, and events are not rewritten.
No cancellation reason is needed; error codes retain their existing meanings.

GET/cancellation schemas include the nullable timestamp. The creation response
schema and JSONB snapshots exclude it, preserving exact creation replays after
stopping. Only the first nonterminal cancellation stamps database UTC time and
appends an ordered cancel_requested event (an intent marker in the existing
16-character event status column, not a run status). A stopped transition adds
its own UUID event under the same per-run ordering/locking rules.

Cancellation and worker paths lock job then run. The unscheduled/enqueue race
restarts the cancellation transaction if a job appeared while acquiring the run
lock, preserving lock order. Authentication/ownership and URL consistency are
rechecked. Inline stopping requires queued plus no job, or a pending, never-claimed
job (zero attempts/fence and no start anchor). Otherwise intent remains durable
until a fenced worker reconciles the runner. Job rows are never deleted for cancel.

Normal terminal completion/failure committed first remains unchanged. Intent
committed first prevents every subsequent normal transition; only acknowledged
stopped may follow. State, intent event, stopped event, and job result commit
atomically where applicable. Repeated requests add no event or new job. Stale
workers cannot append events or change stopped/terminal outcomes.

Backoff is advanced to current database time on cancellation. Normal attempt
counts remain capped at max_attempts; cancellation recovery continues with higher
fences even beyond that budget. Stop transport failures reschedule pending work
with at most 0.25s backoff, retaining intent until acknowledgement. Ordinary
execution failures retain the previous bounded retries. Simulator termination is
deterministic from persisted intent and stable operation identity; no payload or
physical execution is involved.

Disposable migration tests preserve completed/failed jobs, queued unscheduled
runs, and creation snapshots across upgrade/downgrade. Downgrade refuses any
cancellation history rather than silently discard intent or relabel stopped runs.
Development migrations remain upgrade-only, with all volumes and records retained.

## Milestone 7B: PostgreSQL deadlines and shared stop arbitration

`0008_run_expiration` adds nullable timestamptz `runs.expires_at` and
`expiration_requested_at`, and terminal `expired` in run/job state constraints.
Existing deadlines remain null; no old row is scheduled, and no creation snapshot,
fingerprint, cancellation timestamp, or terminal outcome is rewritten.

For API-created runs, a single PostgreSQL clock value supplies created_at and
expires_at = created_at + the validated server lifetime (900s default). Queue time
counts. The partial `(expires_at, id)` index covers only active runs with a deadline
and neither stop intent. Worker discovery uses bounded index scans and separate
short job-then-run locked transactions with SKIP LOCKED. Monotonic local time only
schedules scans, not deadline eligibility. No new scheduler service exists.

`ck_runs_positive_lifetime` requires deadline > created_at when present.
`ck_runs_one_stop_reason` forbids simultaneous cancellation/expiration timestamps.
Under the same run lock, the shared helper preserves any selected intent; otherwise
PostgreSQL time chooses expiration if due, or explicit cancellation before expiry.
Only that reason's timestamp and one ordered intent event are written. Expiration
uses `expire_requested` (an intent marker, not a run status). Fenced acknowledgement
writes `expired` and job result atomically; proven-unstarted queued runs can finish
without calling the runner. Repeated discovery/cancellation cannot duplicate events.

Normal state updates condition on a still-future deadline and absent intents.
The deferred `ck_runs_deadline_commit` constraint trigger also checks PostgreSQL
time at transaction end, preventing a previously inspected normal transition or
outcome from committing after expiry. Its sanitized deadline race rolls back,
then the worker durably selects/reconciles the stop intent. Completed/failed
outcomes already committed before expiry remain terminal. Cancellation selected
first finishes stopped even after the deadline. Neither reason overwrites the
other, and an expired lease never proves a runner did not start.

New creation JSONB snapshots contain the original six fields plus expires_at and
null expiration_requested_at; cancellation remains excluded. Legacy snapshots
retain their original exact stored JSON and field set. GET/cancel representations
add both nullable expiration fields. Replay schema selection uses the stored
snapshot version/fields, never current lifecycle state; fingerprints remain v1.

Retries/claims do not update deadlines. Pending stop reconciliation bypasses long
backoff and ordinary attempt exhaustion, retaining monotonically increasing
fences until stop acknowledgement. No transaction is held across runner calls.
Development migrations are upgrade-only. Disposable downgrade rejects nonnull
deadlines/expiration history instead of silently discarding it. No data or artifact
retention deletion accompanies expiration.
